# Technical architecture options for a Chrome/Brave MV3 crypto-phishing detection extension (as of October 2026)

Scope note: findings below come from primary docs (developer.chrome.com, GitHub repos, arXiv, vendor blogs) fetched in October 2026. Where a page could not be fetched (404) or a claim rests only on secondary sources, this is flagged in Gaps.

## KQ1. MV3 mechanics: URL interception, blocking vs warning page, provider wrapping, service worker lifetime, list storage, remote-code rules, Brave differences

### Takeaway
MV3 gives three usable interception points: `webNavigation.onBeforeNavigate`/`onCommitted` (notification-only, cannot cancel), `declarativeNetRequest` (can block or redirect `main_frame` to an extension page without host permissions when using `block`/`redirect` with `declarativeNetRequest`), and `tabs.update` to redirect after the fact. Remote JSON blocklists are explicitly permitted (only executable code is "remotely hosted code"), so list updates can bypass store review; the service worker dies after 30 s idle, so lists must live in `chrome.storage`/IndexedDB and be refreshed by `chrome.alarms` (min 30 s period).

### Cited Findings
- `webNavigation` event order for a successful navigation is `onBeforeNavigate → onCommitted → [onDOMContentLoaded] → onCompleted`; `onBeforeNavigate` carries `url`, `tabId`, `frameId`; cross-site redirects can fire repeated `onBeforeNavigate` events before the final `onCommitted`; the events are notifications only and the doc does not provide a way to cancel navigation; requires `"webNavigation"` permission — [Chrome webNavigation API](https://developer.chrome.com/docs/extensions/reference/api/webNavigation)
- `tabs.onUpdated` `changeInfo` includes `url` ("the tab's URL if it has changed") and `status` (`unloaded`/`loading`/`complete`); `Tab.url` is only populated if the extension has the `"tabs"` permission or host permission for the page; `tabs.update(tabId, {url})` navigates a tab and the doc says navigating to another URL doesn't require permissions; `javascript:` URLs not supported — [Chrome tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs)
- `declarativeNetRequest`: redirect action can use `"extensionPath"` to send a request to a file inside the extension; that file must be listed in `web_accessible_resources`; rules match `main_frame` only if `resourceTypes` explicitly lists it (default excludes `main_frame`); `block` stops the request before it is sent — [Chrome declarativeNetRequest API](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest)
- `declarativeNetRequest` rule limits: up to 100 static rulesets (50 enabled at once), at least 30,000 enabled static rules guaranteed; dynamic rules total 30,000 of which only 5,000 may be "unsafe" (redirect/modifyHeaders) while safe rules (`block`, `allow`, `allowAllRequests`, `upgradeScheme`) fill the rest; session rules 5,000 (Chrome 120+); regex rules max 1,000 per type, each compiled rule under 2 KB; dynamic rules persist across sessions and are changed via `updateDynamicRules()` without shipping a new package — [Chrome declarativeNetRequest API](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest)
- Permission split: `"declarativeNetRequest"` shows an install-time warning but grants implicit access to `allow`/`allowAllRequests`/`block` without host permissions; `"declarativeNetRequestWithHostAccess"` shows no warning but requires host permissions before acting on a host; `declarativeNetRequestFeedback` (`getMatchedRules`) is for unpacked extensions only; some static ruleset changes "may qualify for expedited review" — [Chrome declarativeNetRequest API](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest)
- Remotely hosted code (RHC) policy: RHC is anything the browser executes loaded from outside the package (JS, WASM named as examples); it "does not include data or things like JSON or CSS"; fetching remote code and executing it, remote `<script>` tags, and RHC pulled in by dependencies are all prohibited; `eval()` is disabled by default (a sandboxed iframe may lift the CSP); violations are rejected with a "Blue Argon" error — [Chrome remote-hosted-code doc](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code)
- Service worker lifecycle: terminated after 30 s of inactivity; a single event/API call longer than 5 minutes is terminated; a `fetch()` response slower than 30 s triggers shutdown; events and extension API calls reset the idle timer (Chrome 110+); messages from an offscreen document (Chrome 109+) and active WebSocket traffic (Chrome 116+) extend life; global variables are lost on shutdown; recommended storage is `browser.storage` (local/session/sync), IndexedDB for structured/large data; Web Storage API (localStorage) is not available in extension service workers; alarms can have a minimum period of 30 s since Chrome 120 — [Chrome service worker lifecycle doc](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle)
- Content scripts: `run_at: "document_start"` injects before any DOM is built or other scripts run; static content scripts accept `world` (`ISOLATED` default, `MAIN` available); MAIN-world scripts follow the page's CSP, not the extension's; isolated-world scripts can use only `dom`, `i18n`, `storage` and some `runtime` members directly; page↔content script communication via `window.postMessage` with `event.source` checks; `match_origin_as_fallback` handles `about:`/`data:`/`blob:` frames — [Chrome content scripts doc](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)
- `host_permissions` are required for `fetch()` to hosts, programmatic injection, `webRequest`, `cookies`, and `declarativeNetRequest` (with-host-access variant); not required for `tabs` API, `debugger`, or manifest-declared content scripts; `optional_host_permissions` are granted at runtime; the doc advises "Consider using optional permissions wherever the functionality of your extension permits" — [Chrome declare-permissions doc](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)
- Brave uses Google Safe Browsing by default on all platforms; on desktop lookups go through a Brave-operated proxy so Google never sees the user's IP; most checks are local hash-prefix lookups; Brave's docs warn "some risky sites may not be identified, and some safe sites may be identified in error" — [Brave: Safe Browsing in Brave](https://support.brave.app/hc/articles/15222663599629-Safe-Browsing-in-Brave)
- Brave Shields lists phishing/malware alerting as a Shields feature — [Brave Shields](https://brave.com/shields/)
- Brave Wallet supports EIP-6963 (multi-injected provider discovery) on desktop, Android and iOS; Brave states it worked with other wallets on the change because MetaMask's `window.ethereum`-only design had become a de facto standard and caused conflicts when several wallets were installed (last-injected wins) — [Brave blog: EIP-6963](https://brave.com/blog/eip-6963/); [EIP-6963 spec](https://eips.ethereum.org/EIPS/eip-6963)
- EIP-6963 discussion notes the announce/request event mechanism is manipulable: an attacker page can override or proxy `dispatchEvent` payloads — [Ethereum Magicians EIP-6963 thread](https://ethereum-magicians.org/t/eip-6963-multi-injected-provider-discovery/14076)
- MetaMask's own extension sanitizes URLs (removing sensitive data) before sending them to MetaMask servers and "select third-party services" for analysis; users can opt out under Settings > Security & Privacy > Basic Functionality — [MetaMask support: Deceptive site ahead](https://support.metamask.io/stay-safe/safety-in-web3/deceptive-site-ahead-when-trying-to-connect-to-a-site)

### Inferences
- Recommended interception design: (1) `declarativeNetRequest` dynamic rules with `resourceTypes: ["main_frame"]` and `redirect.extensionPath` → `/warning.html?...` for the *confirmed* blocklist (zero-latency, works even when the service worker is asleep, no host permissions needed with plain `declarativeNetRequest`); (2) `webNavigation.onCommitted` (or `tabs.onUpdated` with `status: "loading"`) for *heuristic/ML* candidates, followed by `tabs.update` to the warning page or an overlay injected via content script. Because `onBeforeNavigate` cannot cancel, there is always a brief render of the page before `tabs.update` fires; the DNR path avoids that.
- Dynamic-rule budget (30,000 total, 5,000 "unsafe") matters: a redirect rule is "unsafe", so a redirect-based blocklist caps at ~5,000 domains unless you use `block` (safe, up to 30,000) and render the warning via the `onErrorOccurred`/blocked-page path. A pragmatic hybrid: keep the full list (200k+ domains, see KQ2) in `chrome.storage`/IndexedDB for JS lookup, and push only the hottest ~5,000 into DNR redirect rules.
- Fetching `domains.json` from GitHub/your CDN is squarely "data not code" and allowed; only the parser/classifier must ship in the package. ONNX/WASM models are a grey zone because the doc names WASM as RHC — bundle `.wasm` and `.onnx` files in the package rather than fetching them remotely (model weights are data, but to be safe ship the runtime binary locally).
- On Brave, Safe Browsing (proxied) already covers generic phishing; a crypto-specific extension's value is the crypto feeds (ScamSniffer, MetaMask) and provider-level signature warnings, which Brave's lists don't cover. Brave Wallet injects its own `window.ethereum`; a MAIN-world wrapper should use EIP-6963 announce events to enumerate all providers rather than assume a single `window.ethereum`.

### Gaps
- Chrome version thresholds for `world: "MAIN"` in static content scripts and `scripting.executeScript` were not stated on the fetched page (believed Chrome 111+ for static, 95+ for executeScript, but unverified here).
- Whether `chrome.storage` calls reset the service worker idle timer is not explicitly stated (the doc only says extension API calls in general do, Chrome 110+).
- The CSP directive for bundled WASM (`'wasm-unsafe-eval'`) was not covered by the fetched pages.
- No Brave-specific documentation on how Brave Shields interacts with third-party extension DNR rules or whether Brave maintains a crypto-specific phishing list beyond proxied Safe Browsing was found.
- Offscreen documents: only the lifecycle note (messages from offscreen docs keep the worker alive, Chrome 109+) was found; no fetched source on using offscreen docs to host ONNX/WebGPU inference.

## KQ2. Open-source reference extensions: MetaMask phishing-controller/phishing-warning, ScamSniffer, Wallet Guard, Revoke.cash, Pocket Universe, uBlock Origin Lite, others

### Takeaway
The dominant open-source reference is MetaMask's `phishing-controller` (in `MetaMask/core`): a 30-day full "stalelist" + 5-minute "hotlist" diff feed, plus a separate 5-minute SHA-256-hashed C2 domain blocklist and a server-side `scanUrl` API that returns a `RecommendedAction`. Most standalone competitors (Wallet Guard, Revoke.cash extension, Fire) have been acquired or sunset; ScamSniffer and Pocket Universe (now Kerberus) remain, and ScamSniffer's open data is a 7-day-delayed GPL-3 JSON list.

### Cited Findings

- MetaMask says the eth-phishing-detect blocklist has more than 205,000 malicious domains, reviewed by MetaMask staff with contributions from ChainPatrol, SEAL and 100+ community members; new sites show a warning "within minutes of detection" — [MetaMask + ChainPatrol news](https://metamask.io/news/metamask-chainpatrol-protect-users-with-phishing-warnings)

### Inferences
- The MetaMask pattern (big stalelist refreshed rarely + small signed diff feed every 5 min + session-scoped bypass) is the proven list-distribution architecture and maps cleanly onto MV3: alarms at 5 min, diffs applied to `chrome.storage.local`/IndexedDB, hashed C2 list for request-level blocking without leaking the full list. Hashing hostnames (SHA-256) for the C2 list is also a way to distribute a sensitive list without disclosing the raw domains.
- Warning UX in the ecosystem is "redirect to an extension-owned full page" (MetaMask) for navigation blocks and "popup window at signature time" (Revoke.cash, Pocket Universe, Wallet Guard) for transaction-level warnings. A new extension should implement both layers.
- The market lesson is consolidation: three of the best-known standalone defenders (Wallet Guard, Fire/Blowfish-era products, Revoke.cash extension) exited or were absorbed within 2024–2026; a sustainable standalone extension needs a distribution/revenue model (ScamSniffer uses a DEX-fee premium tier; Pocket Universe sells per-transaction coverage).
- ScamSniffer's open list being 7 days delayed means it is useful mainly as *training/evaluation* data, not as a real-time feed; the real-time feed is $999/month.

### Gaps
- The MetaMask extension's own navigation handler (how it listens and redirects to `phishing.html` with hostname/href hash params, and how "continue anyway" calls `bypass`) could not be fetched (GitHub blob 404 for the guessed path); only the controller side is documented above.
- The Levenshtein/fuzzylist tolerance implementation lives in `PhishingDetector`/`utils.ts`, which was not fetched; the controller only stores `fuzzylist` and `tolerance`.
- No canonical ScamSniffer extension source repo URL was found; the "AGPL-3.0, 48 stars" claim is from AlternativeTo only.
- Fire extension status and Netcraft / Bitdefender TrafficLight architectures were not researched (no calls spent); ScamSniffer `domains.json` schema and entry count were not visible on the repo page.
- Wallet Guard repo: manifest version, last-commit date and whether it is archived were not shown on the fetched page.

## KQ3. URL/domain ML classifiers: model families, accuracy, sizes, in-browser runtimes, training data, pitfalls

### Takeaway
The best-documented fully client-side model is PhishLang (NDSS; MobileBERT, 25M params, ~74 MB RAM, median 390 ms inference, F1 0.96 on a 30k/30k split, ~3% estimated FPs in the wild). URL-only gradient-boosted models (e.g. a LightGBM exported to ONNX at ~0.7–0.9 MB) exist on Hugging Face and run under ONNX Runtime Web's WASM provider, but published accuracy for crypto-specific URLs is lacking.

### Cited Findings
- PhishLang (arXiv 2408.05667, NDSS): MobileBERT-based, analyzes page source context; trained on PhishPedia base (30K phishing / 30K benign; 22,419 phishing and ~26K benign with HTML), 70/30 split, 5-fold CV, 10 epochs; test metrics Accuracy 0.96 / Precision 0.95 / Recall 0.96 / F1 0.96; median inference 0.39 s; 74 MB DRAM; 25M parameters; peak RAM 28–247 MB; runs on 1 GB RAM single-core CPU — [PhishLang arXiv HTML](https://arxiv.org/html/2408.05667v2)
- PhishLang comparison table: DistilBERT F1 0.94, 0.85 s, 502 MB; also TinyBERT, DeBERTa, FastText, GPT-2, Llama-2-7B, T5-base, Bloom were evaluated; cites Pourmohamad et al. that Google Safe Browsing detects only 14% of phishing sites without server-side support — [PhishLang arXiv HTML](https://arxiv.org/html/2408.05667v2)
- PhishLang real-world run: scanned 42.7M domains (~172M pages) from Sept 28 2023 to Jan 11 2024, flagged 25,796 (0.057%); of 2.5k manually checked, 2,388 confirmed phishing (~94% regular, ~91% evasive categories; Cohen's kappa 0.82); authors estimate ~3% false positives; adversarial testing with 16 problem-space attacks showed false negatives up to 20.92% before patches, dropping to 0–1.68% after adversarial retraining; added 411 "Behavioral JS Evasion" samples from 17,305 PhishTank-verified sites (July 2024) — [PhishLang arXiv HTML](https://arxiv.org/html/2408.05667v2)
- PhishLang extension implementation: Chromium-based, with "a background process that runs the MobileBERT model as a local server" (i.e. not pure in-extension inference); Windows 10+ and Debian-based Linux, macOS "coming soon"; pairs with GPT-3.5 Turbo for explanations — [PhishLang arXiv HTML](https://arxiv.org/html/2408.05667v2); [NDSS listing](https://www.ndss-symposium.org/ndss-paper/phishlang-a-real-time-fully-client-side-phishing-detection-framework-using-mobilebert)
- PhishScout v2 (Hugging Face): LightGBM URL-structure-only classifier exported to ONNX, "runs anywhere ONNX Runtime runs, including in the browser through ONNX Runtime Web"; model card lists 896.3 KB total and a 669 KB ONNX file (internally inconsistent) — [PhishScout-v2 model card](https://huggingface.co/saidutta69/PhishScout-v2)
- PhishPatrol (Chrome Web Store): uses an ONNX-optimized DeBERTa model but sends data to an external API (not fully local) — [PhishPatrol listing](https://chromewebstore.google.com/detail/mhepgdmaljmmajhdchlcecdokeknofen)
- A journal paper (SEU JICT vol. 3 issue 2) reports an XGBoost URL-feature model at ~90% accuracy with inference on a backend API — [SEU JICT PDF](https://www.seu.ac.lk/jict/publication\vl03is02\55-64%20Real-Time%20URL-Based%20Phishing%20Detection.pdf)
- ONNX Runtime Web execution providers: `wasm` (alias `cpu`), `webgl`, `webgpu`, `webnn` (gpu or cpu deviceType); "All ONNX operators are supported by WASM" but only a subset by WebGL/WebGPU/WebNN; ORT-format models reduce binary size, init time and peak memory; custom builds can include only needed operators — [ONNX Runtime Web tutorials](https://onnxruntime.ai/docs/tutorials/web/)
- Tranco: 1M-domain research ranking averaging Cisco Umbrella, Majestic, CrUX and Cloudflare Radar over 30 days (Farsight in default list), updated daily by 00:00 UTC, permanent `/top-1m.csv.zip`; licenses differ (CrUX CC BY-SA 4.0, Cloudflare Radar CC BY-NC 4.0 non-commercial, Majestic CC BY 3.0); the paper warns rankings disagree, change daily, and can be manipulated — [tranco-list.eu](https://tranco-list.eu/)
- MetaMask's own blocklist uses CoinMarketCap-derived popular-domain safeguard lists to prevent false positives; blocking a safeguarded domain requires an explicit bypass entry — [eth-phishing-detect](https://github.com/MetaMask/eth-phishing-detect)

### Inferences
- A practical two-tier client-side design: tier 1 = exact/fuzzy list lookup (MetaMask stalelist+hotlist, ScamSniffer open list, local Levenshtein against a brand list) in <1 ms; tier 2 = a sub-1 MB URL-feature GBDT/logistic model in ONNX Runtime Web (WASM) that runs on every `onCommitted`; tier 3 = a heavier content model (MobileBERT-class, ~75 MB RAM, ~400 ms) or an LLM (KQ4) only for pages that pass tier 2 above a threshold *and* touch a wallet provider (e.g. call `eth_requestAccounts`/`personal_sign`). This bounds per-navigation cost and keeps memory low.
- PhishLang's "local server" packaging shows that a 25M-param transformer was not run inside the extension itself in 2024; with ONNX Runtime Web + WebGPU in 2026 it is plausible to run in an offscreen document, but no fetched source demonstrates it for an MV3 extension.
- Training-data pitfalls: PhishLang's own appendix shows FNs rising to ~21% under evasion until retrained — concept drift and adversarial retraining must be budgeted as an ongoing pipeline, not a one-off. Tranco's non-commercial Cloudflare Radar component means a commercial product should build its benign set from the CC-BY sources or from crypto-specific allowlists (MetaMask allowlist, DefiLlama/CoinGecko link sets).
- Crypto phishing is dominated by brand impersonation on fresh domains (ScamSniffer-style lists) rather than generic credential phishing; a URL-only model trained on PhishTank/OpenPhish will underperform on wallet-drainer sites unless the positive set includes ScamSniffer `domains.json` history and MetaMask blocklist git history.

### Gaps
- No peer-reviewed 2024–2026 paper was found that reports accuracy for a *crypto-specific* URL classifier, nor one that benchmarks ONNX Runtime Web / TF.js inference latency inside an MV3 extension.
- ONNX Runtime Web WASM bundle sizes, SIMD/threads requirements and the extension CSP needed were not on the fetched page.
- PhishScout's dataset, accuracy, and FP rates were not retrieved (model card numbers are self-reported and inconsistent).
- No source quantifying TLD overfitting or dataset bias specifically for crypto phishing corpora was found.

## KQ4. LLM-based classification: cloud vs on-device, cost, latency, privacy, prior art (Chrome Gemini Nano, Edge Scareware Blocker, Prompt API)

### Takeaway
Google and Microsoft both ship on-device scam detection in the browser (Chrome 137 Gemini Nano for tech-support scams, Edge Scareware Blocker computer-vision model), but both trigger only on narrow signals and send nothing (or only LLM-summarized signals under Enhanced Protection) to the cloud. Chrome's Prompt API is usable from extensions (with a now-expired origin-trial permission to remove), supports image input, and requires ~22 GB free disk and >4 GB VRAM or 16 GB RAM — too heavy to rely on as a baseline. Cloud LLM triage on candidate pages costs on the order of $0.001–0.003 per page with Claude Haiku 4.5.

### Cited Findings
- Chrome 137 (May 2025) uses on-device Gemini Nano to generate security signals for Safe Browsing against tech-support scams; the LLM runs only when a page shows scam-typical behavior (example trigger: keyboard lock API use); Chrome gives the model the page contents and asks it to extract signals such as apparent intent; only LLM-summarized signals are sent to Safe Browsing and only for Enhanced Protection users; processing is asynchronous with GPU throttling and quotas; motivation: "the average malicious site exists for less than 10 minutes"; planned expansion to package-tracking and unpaid-toll scams, Android, and research on prompt-injection and timing bypasses — [Google Security blog](https://blog.google/security/using-ai-to-stop-tech-support-scams-in/)
- Chrome Prompt API for extensions: extension developers should remove the expired trial permission `"aiLanguageModelOriginTrial"`; supported on Windows 10/11, macOS 13+, Linux, Chromebook Plus; requires at least 22 GB free disk (model removed if free space drops below 10 GB), a GPU with >4 GB VRAM or a CPU with 16 GB+ RAM and 4+ cores; multimodal input supports images (HTMLImageElement, Canvas, ImageBitmap, Blob, ImageData, etc.) and audio, text output only; languages English, Japanese, Spanish, German, French; API surface `LanguageModel.availability()/create()/prompt()/promptStreaming()`, `responseConstraint` (JSON schema), `contextWindow`, `QuotaExceededError`; no data goes to Google during use; model download needs user activation; Web Workers unsupported on the web — [Chrome Prompt API doc](https://developer.chrome.com/docs/extensions/ai/prompt-api)
- A secondary source states the Prompt API has shipped in Chrome from version 138 and reports a May 2026 controversy about Chrome downloading the ~4 GB model without explicit consent — [nevercodealone.de glossary (secondary, unverified)](https://nevercodealone.de/glossare/ki-tools-2026/gemini-nano-on-device-llm-chrome-pixel-built-in-ai-2026)
- Microsoft Edge Scareware Blocker (Edge dev blog, Jan 27 2025): compares full-screen pages to "thousands of sample scams" shared by the scam-fighting community using computer vision; model runs locally "without saving or sending images to the cloud"; on detection Edge exits full screen, stops aggressive audio, warns and shows a thumbnail; introduced at Ignite Nov 2024, preview in stable channel — [Microsoft Edge dev blog](https://blogs.windows.com/msedgedev/2025/01/27/stand-up-to-scareware-with-scareware-blocker/); [BleepingComputer](https://www.bleepingcomputer.com/news/microsoft/microsoft-tests-edge-scareware-blocker-to-block-tech-support-scams/)
- TechRadar later reported it is enabled by default on devices with at least 2 GB RAM and four CPU cores; commentators questioned running a model on every page on older machines — [TechRadar](https://www.techradar.com/pro/security/microsoft-is-finally-clamping-down-on-scam-attacks-with-new-scareware-sensor-heres-what-you-need-to-know); [TechCrunch](https://techcrunch.com/2025/01/28/microsoft-tests-scareware-blocker-for-edge-that-uses-computer-vision-to-detect-scams)
- Claude Haiku 4.5 list pricing: $1.00 per million input tokens, $5.00 per million output tokens; cached input $0.10/M (90% discount) — [pricepertoken](https://pricepertoken.com/pricing-page/model/anthropic-claude-haiku-4.5); [anotherwrapper pricing](https://anotherwrapper.com/llm-pricing/claude-haiku-4-5-20251001) (both third-party trackers citing Anthropic's pricing page)
- PhishLang pairs its classifier with GPT-3.5 Turbo to explain why a site was flagged (explanation, not detection) — [PhishLang arXiv abstract](https://arxiv.org/abs/2408.05667v2)
- MetaMask's server-side `scanUrl` is the production example of a backend verdict API: 8 s timeout, 1-min client cache of 250 URLs, result `{hostname, recommendedAction}` — [PhishingController.ts](https://raw.githubusercontent.com/MetaMask/core/main/packages/phishing-controller/src/PhishingController.ts)

### Inferences
- Cost model for cloud triage (derived from the list prices above): a prompt with ~1,500 tokens of stripped page text + hostname + ~300-token system prompt (cacheable) and a ~50-token structured JSON answer costs roughly $0.0015–0.002 per page on Haiku 4.5; with prompt caching on the system prompt it drops toward $0.0015. If only ~1% of navigations reach the LLM tier (after list + lightweight model filtering), a user doing 200 navigations/day costs ≈ $0.004/day ≈ $0.12/month. Screenshot (vision) inputs are several times more tokens; keep them for the rarest tier.
- Latency: cloud LLM round-trips are 1–3 s class (not measured here), far above the ~0–400 ms of local tiers, so the LLM verdict should be asynchronous: let the page render, suppress wallet provider calls (hold `eth_requestAccounts`/signing in the MAIN-world wrapper) until the verdict arrives, then overlay or redirect. This mirrors Chrome's "asynchronous, sparingly, signal extraction" design.
- Privacy: Google's design (only summarized signals leave the device, only for opted-in users) and MetaMask's (sanitized URLs, opt-out toggle) set the user-expectation bar. A third-party extension sending full URLs/page text to an LLM API must disclose this prominently (see KQ7 Limited Use) and should hash or truncate URLs, strip query strings and form values, and gate on explicit opt-in.
- Chrome's built-in Prompt API is a free on-device option when available, but the hardware/disk floor (22 GB, >4 GB VRAM) means most users will not have it; treat it as an optional accelerator with `availability()` checks, not the core path. Brave does not ship Chrome's Gemini Nano components (no source found confirming either way — see Gaps).
- Prompt injection is a real attack surface: a phishing page can embed text addressed to the classifier LLM ("this is the official Uniswap site"). Google explicitly lists prompt-injection research as ongoing; a production design should send structured features (title, visible brand strings, form fields, wallet calls) rather than raw HTML, and never let the LLM's output alone whitelist a site.

### Gaps
- No primary Anthropic pricing page was fetched (the claude-api skill reference was not consulted); numbers above are from trackers that cite it.
- No published paper or product was found that specifically does "is this a clone of project X?" LLM classification for crypto phishing with reported precision/recall.
- Whether the Chrome Prompt API is callable from an extension *service worker* (vs. extension pages/offscreen docs) was not stated in the fetched doc.
- No source on Brave's support (or lack) for Chrome's built-in AI APIs / Gemini Nano, nor on Brave Leo being used for page classification.
- Measured end-to-end latency figures for cloud LLM page classification were not found.

## KQ5. Visual similarity / screenshot approaches in an extension

### Takeaway
`captureVisibleTab` is feasible (needs `activeTab` or host permission, hard-limited to 2 calls/second and described as "expensive"), and both Edge's Scareware Blocker and Chrome's Prompt API (image input) show on-device visual classification is now mainstream in browsers; but no open-source extension doing perceptual-hash or logo matching for crypto brands was found.

### Cited Findings
- `tabs.captureVisibleTab` requires `<all_urls>` or `activeTab` (host permissions also suffice); sensitive pages (chrome://, other extensions, data: URLs) only with `activeTab`; `MAX_CAPTURE_VISIBLE_TAB_CALLS_PER_SECOND` = 2 (Chrome 92+); the doc says it "is expensive and should not be called too often" — [Chrome tabs API](https://developer.chrome.com/docs/extensions/reference/api/tabs)
- Edge Scareware Blocker uses a local computer-vision model over full-screen page renders, compared against thousands of community-shared scam samples; images are not saved or sent to the cloud — [Microsoft Edge dev blog](https://blogs.windows.com/msedgedev/2025/01/27/stand-up-to-scareware-with-scareware-blocker/)
- Chrome's Prompt API accepts image inputs (ImageBitmap, Canvas, Blob, etc.) from extensions, so a captured screenshot can be classified on-device where the model is available — [Chrome Prompt API doc](https://developer.chrome.com/docs/extensions/ai/prompt-api)
- urlscan.io stores screenshots (`https://urlscan.io/screenshots/$uuid.png`) and DOM snapshots (`https://urlscan.io/dom/$uuid/`) for scans, and offers brand detection ("Pro Only") in search results — [urlscan.io API docs](https://urlscan.io/docs/api/)
- PhishLang's training base is PhishPedia (30K/30K), a dataset originally built for visual/logo-based phishing detection — [PhishLang arXiv HTML](https://arxiv.org/html/2408.05667v2)

### Inferences
- A cheap visual signal that needs no screenshot permission: fetch the page's favicon and `<img>` logo URLs from the content script, compute a perceptual hash in WASM/JS, and compare to a bundled table of hashes for the top ~500 crypto brands; a logo match on a hostname not in the brand's allowlist is a strong clone indicator. This avoids `captureVisibleTab`'s permission and rate limits and runs in the isolated world.
- Full screenshots should be reserved for the final tier (after a wallet interaction is attempted), captured once, and either classified locally via the Prompt API when `availability()` is "available", or sent to a vision-capable cloud model under opt-in.
- urlscan.io screenshots/DOMs of ScamSniffer/MetaMask-listed domains are a ready-made corpus for training/validating a visual-similarity model without crawling live phishing pages yourself.

### Gaps
- No open-source extension implementing perceptual hashing or logo matching for crypto phishing was found in this research.
- No fetched source gives accuracy numbers for Phishpedia/PhishIntention/VisualPhishNet-style models in 2024–2026 or their feasibility in WASM.

## KQ6. Evaluation methodology: corpora, metrics, production FP monitoring

### Takeaway
Positive corpora with history exist (MetaMask eth-phishing-detect git history with 200k+ domains, ScamSniffer `domains.json` with daily refresh and 7-day public delay, PhishTank, urlscan.io search), benign sets come from Tranco (with license caveats) and MetaMask's allowlist/safeguard lists; the production FP loop used by MetaMask is a public GitHub issue queue plus session-scoped bypass.

### Cited Findings
- eth-phishing-detect has 257,036 commits and >205,000 blocked domains, giving a dated history of additions/removals; false-positive safeguards are plaintext popular-domain lists in `test/resources` refreshed from CoinMarketCap — [eth-phishing-detect](https://github.com/MetaMask/eth-phishing-detect); [MetaMask news](https://metamask.io/news/metamask-chainpatrol-protect-users-with-phishing-warnings)
- ScamSniffer `blacklist/domains.json` and `address.json`, refreshed every 24 h with a 7-day public delay, 1,451 commits — [scam-database](https://github.com/scamsniffer/scam-database)
- urlscan.io Search API: `GET /api/v1/search/?q=<ElasticSearch query>`, `size` default 100 up to 10,000 by subscription, `search_after` pagination, exact counts only to 10,000; rate limits per minute/hour/day with 429 and `X-Rate-Limit-*` headers (only HTTP 200 counts against quota); submission `POST /api/v1/scan/` with `visibility` public/unlisted/private and up to 10 tags; brand detection is Pro-only — [urlscan.io API docs](https://urlscan.io/docs/api/)
- Tranco 1M, daily, four-source average; CrUX CC BY-SA 4.0, Cloudflare Radar CC BY-NC 4.0, Majestic CC BY 3.0; authors recommend recording download/visit dates and reachability for reproducibility — [tranco-list.eu](https://tranco-list.eu/)
- PhishLang's evaluation protocol: 70/30 split with 5-fold CV, a separate 6,725-URL adversarial set, a live 3.5-month scan with manual verification of 2.5k flags by raters (kappa 0.82), and immediate reporting of all flags — [PhishLang arXiv HTML](https://arxiv.org/html/2408.05667v2)
- MetaMask FP process: site owners open a GitHub issue; a team member reviews and may allowlist; ChainPatrol offers a tool to check why a domain was blocked; a Railway community thread documents one project whose domain was flagged and later confirmed as a false positive and removed — [MetaMask support](https://support.metamask.io/stay-safe/safety-in-web3/deceptive-site-ahead-when-trying-to-connect-to-a-site); [Railway thread](https://station.railway.com/questions/my-account-takerprotocol-team-gmail-com-176f8796)
- MetaMask's controller implements session bypass (`bypass(origin)`), path-scoped whitelisting for shared hosts (IPFS gateways, sites.google.com), and a 1-minute URL-scan cache — [PhishingController.ts](https://raw.githubusercontent.com/MetaMask/core/main/packages/phishing-controller/src/PhishingController.ts); [CHANGELOG](https://raw.githubusercontent.com/MetaMask/core/main/packages/phishing-controller/CHANGELOG.md)
- Brave's own Safe Browsing docs acknowledge "some safe sites may be identified in error" — [Brave support](https://support.brave.app/hc/articles/15222663599629-Safe-Browsing-in-Brave)

### Inferences
- Build a time-split test set: use `git log -p` over eth-phishing-detect `config.json` and ScamSniffer `domains.json` to get domain + first-seen date; train on domains first seen before date T, test on those after T (this measures concept drift, which random splits hide). Use urlscan.io search (`task.tags:phishing` or brand filters, Pro for brand) to pull HTML/screenshots for each domain while they are still live, since drainer domains die within days.
- Benign set must be crypto-heavy to catch TLD/keyword overfitting: MetaMask allowlist, the eth-phishing-detect safeguard lists, DefiLlama/CoinGecko link exports, plus general Tranco top-N (avoid Cloudflare Radar-derived lists for commercial use). Report precision at a fixed, very low FP budget (e.g. FPR ≤ 0.1% on crypto-benign) rather than accuracy, because every FP on a real DeFi site damages trust far more than a miss.
- Production loop: (1) every block page carries "Report false positive" that posts hostname + list source + model score (no page content) to your backend; (2) auto-allowlist after N confirmed reports or manual review; (3) session bypass like MetaMask; (4) opt-in telemetry of block/bypass ratio per list source so a noisy feed can be demoted; (5) path-scoped blocks for shared hosts (IPFS gateways, GitHub Pages, Vercel) so one phishing subpath doesn't block the whole host.

### Gaps
- PhishTank and OpenPhish API terms/rate limits were not fetched.
- No published count of MetaMask false-positive appeals or median resolution time was found.
- No source documents a standard "crypto phishing benchmark" dataset with agreed metrics.

## KQ7. Distribution: Chrome Web Store review, Limited Use, Brave compatibility, data vs code update cadence

### Takeaway
Chrome Web Store policy requires "the narrowest permissions necessary", and the Limited Use policy prohibits collecting browsing activity except for a user-facing feature that is prominently described; broad host permissions are documented by third parties as triggering in-depth review. List updates shipped as JSON data are not "remotely hosted code" and need no review, whereas DNR static rulesets inside the package do (with possible expedited review); Brave installs Chrome Web Store extensions and runs proxied Safe Browsing alongside them.

### Cited Findings
- Chrome Web Store permissions policy: "Request access to the narrowest permissions necessary to implement your Product's features or services"; choose the permissions with least data access when several would do; don't request permissions for unbuilt features — [CWS permissions policy](https://developer.chrome.com/docs/webstore/program-policies/permissions)
- Limited Use policy: applies to raw and derived/aggregated data; "Collection and use of web browsing activity is prohibited, except to the extent required for a user-facing feature described prominently in the Product's Chrome Web Store page and in the Product's user interface" — [CWS Limited Use policy](https://developer.chrome.com/docs/webstore/program-policies/limited-use/)
- Third-party developer guides say `<all_urls>` in `content_scripts.matches` or wildcard `host_permissions` triggers an "in-depth review" warning in the developer dashboard and often longer review or rejection (not verified against Google documentation) — [extensionbooster blog](https://extensionbooster.net/blog/chrome-extension-host-permission-in-depth-review-warning-fix-guide.md); [claudecodeguides](https://claudecodeguides.com/chrome-extension-permissions-too-many/)
- RHC policy: JSON/CSS data fetched remotely is not RHC; executable JS/WASM is; violations rejected with "Blue Argon"; appeals via One Stop Support — [Chrome RHC doc](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code)
- DNR: dynamic rules are updated in JS without a new package; static ruleset file changes are part of the package, and some static ruleset changes "may qualify for expedited review" — [Chrome declarativeNetRequest API](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest)
- uBO Lite experience: bundled lists update only with a store release; the developer reports Chrome Web Store review sometimes "takes very long"; a forum post claims filter-list-only updates are expedited and uBOL ships roughly every 2 days — [uBOL release notes](https://newreleases.io/project/github/uBlockOrigin/uBOL-home/release/2026.729.1529); [Privacy Guides thread](https://discuss.privacyguides.net/t/inaccurate-statement-in-the-browser-extensions-section/28090)
- `optional_host_permissions` lets users grant host access at runtime; the doc advises optional permissions wherever possible because users trust extensions with fewer warnings — [Chrome declare-permissions doc](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions)
- Brave applies Google Safe Browsing (via Brave proxy) by default on all platforms, independent of extensions — [Brave support](https://support.brave.app/hc/articles/15222663601629-Safe-Browsing-in-Brave)
- Comparable extensions' store footprints: Wallet Guard ~100K users, 4.7 rating/565 reviews before sunset; Pocket Universe ~100K users (listing says 200K+), v1.9.0 May 2026; ScamSniffer 50K+ users, v0.0.60 Feb 2025 — [Wallet Guard listing](https://chrome.google.com/webstore/detail/wallet-guard/pdgbckgdncnhihllonhnjbdoighgpimk); [Pocket Universe listing](https://extensionauditor.com/scan/pocket-universe-gacgndbocaddlemdiaadajmlggabdeod); [ScamSniffer listing](https://extensionauditor.com/scan/scam-sniffer-mnkbccinkbalkmmnmbcicdobcmgggmfc)
- MetaMask discloses sending sanitized URLs to its servers and third parties with an opt-out, which is the disclosure pattern a Limited-Use-compliant security extension follows — [MetaMask support](https://support.metamask.io/stay-safe/safety-in-web3/deceptive-site-ahead-when-trying-to-connect-to-a-site)

### Inferences
- Permission strategy to minimize review friction: use `declarativeNetRequest` (not the WithHostAccess variant) for list blocking (no host permissions needed), `webNavigation` + `tabs` for URL observation, and a MAIN-world content script on `<all_urls>` only for the provider wrapper. `<all_urls>` content scripts will still trigger in-depth review; justify it in the listing as the single purpose ("warn before connecting a wallet to a phishing site") and describe all data flows (URL hashes sent to backend, opt-in LLM analysis) prominently to satisfy Limited Use.
- Cadence: ship code every few weeks through store review; ship list diffs every 5 minutes as JSON from your CDN (allowed); push DNR *dynamic* rules from those diffs; never rely on static rulesets for anything time-sensitive.
- Brave compatibility is essentially Chrome compatibility, with two caveats: Brave Shields may block your backend/CDN calls if the domain lands on a tracker list (use a first-party domain), and Brave Wallet's injected provider must be handled via EIP-6963.

### Gaps
- Google's own documentation of "in-depth review" triggers for broad host permissions was not found; only third-party blogs describe it.
- The full CWS Program Policies page (single purpose, "deceptive behavior") was not fetched.
- No Brave-specific extension store policy or Brave add-on review process documentation was found (Brave uses the Chrome Web Store).
- Whether DNR static ruleset-only updates actually receive expedited review in practice (and how fast) is unverified beyond the uBOL anecdote.
