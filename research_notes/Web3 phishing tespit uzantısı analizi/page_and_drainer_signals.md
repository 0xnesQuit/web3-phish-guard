# Page-content and runtime signals that identify crypto wallet-drainer pages (and how legitimate dApps differ) — as of October 2026

Scope note: This file covers in-page / runtime signals that an MV3 content script could evaluate. Domain/URL reputation, on-chain address intelligence and transaction simulation are only referenced where they interact with page-side detection. Exploit code is not reproduced; only detection-relevant behaviour is described.

---

## KQ1. Drainer-as-a-service kits: front-end JS structure, loading, obfuscation, public fingerprints / IOCs

### Takeaway
Every well-documented kit (Inferno, Angel, Pink, CLINKSINK/Chick/Rainbow on Solana) ships as one or a few heavily obfuscated JS files that an affiliate pastes into a cloned HTML page; the real logic (which assets to take, which signature to request) is decided server-side (C2) and increasingly fetched from on-chain or proxy endpoints. The only public, page-side fingerprints are (a) kit file names in the HTML (`settings.js`/`webchunk.js` for Angel, `contract.js`/`main.js`/`vendor.js` for Pink, UUID-named JS plus `./scripts/seaport.js` and `./scripts/wallet_connect.js` for Inferno), (b) Mandiant's CLINKSINK YARA rule (function names such as `createPrizeTxs`, `claimSolana`), and (c) Check Point's Inferno strings (`inferno`, `rotatingURL_koy`, `secureproxy.php`, `ping_proxy`, multicall `aggregate3` to BSC). No vendor publishes a maintained open signature list for drainer JS; domain blocklists (ScamSniffer scam-database, MetaMask eth-phishing-detect) are the only open IOC feeds.

### Cited Findings

**Kit landscape and status (historical vs active)**

Pussy and Venom "have ceased their criminal activities". Total: $135M from 76,582 victims, 1,910 profit-sharing contracts, 56 operators, 6,087 affiliates — [IMC'25 paper PDF](https://assets.blocksec.com/pdf/1761189308551-2.pdf); summarised by [BlockSec](https://blocksec.com/blog/inside-ethereum-s-shadow-economy-new-research-unmasks-the-135-m-drainer-as-a-service-industry)

**How the front-end is structured and loaded**
- Inferno toolkit HTML snippet that affiliates must paste into their cloned page (Listing 2 of the IMC'25 paper): ethers 5.6.9 UMD from a CDN, `merkletreejs@latest` from jsDelivr, local `./scripts/seaport.js`, local `./scripts/wallet_connect.js`, `sweetalert2@11` from jsDelivr, and a local UUID-named file (`./8839a83b-968a-46d3-a3ee-96bbf497b662.js`). "Affiliates are instructed to clone the websites of popular projects and subsequently embed this HTML code snippet"; "the HTML code and Javascript files form the fingerprints of these drainers" — Angel: `settings.js`, `webchunk.js`; Pink: `contract.js`, `main.js`, `vendor.js`. The authors built a dataset of 867 toolkit fingerprints and used CT-log keyword monitoring (63 keywords such as "claim", "airdrop", "mint", plus Levenshtein ratio >0.8 variants) + urlscan crawling to find 32,819 DaaS phishing sites between 1 Dec 2023 and 1 Apr 2025; top TLDs .com 30.0%, .dev 13.6%, .app 11.6% — [IMC'25 paper](https://assets.blocksec.com/pdf/1761189308551-2.pdf)
- Check Point (2025): Inferno drainer is "a single obfuscated JavaScript file of 5–10 MB with UUID-like filenames that rotate every few days"; obfuscation = function-based string indexing, split-and-concatenate helpers (names seen: `XeB8Fcz`, `XIfqRhC`, `EM8p5y`), dynamic property access (`'cal'+'l'`), arithmetic-encoded indices, recursive multi-layer obfuscation; anti-debugging via dynamically built functions containing `debugger` statements; client-side fallback list `rotatingURL_koy` pointing to koyeb.app hosts — [Check Point Research](https://research.checkpoint.com/2025/inferno-drainer-reloaded-deep-dive-into-the-return-of-the-most-sophisticated-crypto-drainer/)
- Inferno C2 discovery is on-chain: the script issues `eth_call` to BSC (chain 56) RPCs (`rpc.ankr.com/bsc`, `bsc-dataseed2.bnbchain.org`), reads a "RemotePatchConfig" contract `0x158862Ec60B7934f1333e53AC1e148811A2E3BeB` (feature toggles; WebSocket/WebRTC/HTTP protocol settings) and an encrypted C2 contract `0xd24aeC3254652B0ab565E41A945b491e98Bb5FFC`; a variant calls Multicall3 `aggregate3` (`0xca11bde05977b3631167028862be2a173976ca11`) against `0x72cD63650700E5395f4aB238cecD18497A33a83e`, whose return value is base64 → ROT13 → URL. Check Point's detection hint: "Watch for `eth_call` JSON-RPC requests from web pages to BSC endpoints, especially `aggregate3` against Multicall3 with many calls that have `allowFailure: true`" — [Check Point Research](https://research.checkpoint.com/2025/inferno-drainer-reloaded-deep-dive-into-the-return-of-the-most-sophisticated-crypto-drainer/)
- Inferno "Secure Proxy": a PHP relay (`secureproxy.php`, class `SecureProxyMiddleware`) on affiliate hosts since March 2025; endpoint passed in GET param `e`; `e=ping_proxy` returns "pong", missing `e` returns HTTP 400 "Missing endpoint"; other C2 on `*.workers.dev`. C2 JSON bodies use nested CryptoJS/OpenSSL "Salted__" AES layers, outer key literally `inferno`, inner date-derived keys; request fields `walletAddress`, `walletName`, `site`, `fingerprintData` (incl. `visitorId`), `logs`; log event names `site_loaded`, `modal_open`, `request_connect`, `connect`, `connect_too_low`, `connect_but_seed_prompt`, `switch_chain_prompt`, `verify_sign_prompt`; script version field (e.g. `7.19`) and embedded encrypted customer ID; each affiliate gets a uniquely obfuscated script — [Check Point Research](https://research.checkpoint.com/2025/inferno-drainer-reloaded-deep-dive-into-the-return-of-the-most-sophisticated-crypto-drainer/)
- Inferno (2024 sample, independent RE): "a single line of messy-looking JavaScript" with runtime string decoder calls, control-flow indirection and dead code; contains "a defense mechanism that repeatedly triggers breakpoints when the debugger is open"; it also "creates a counterfactual contract address locally and sends it to the backend to evade anti-phishing browser extensions" — [Mueller, "Reverse Engineering Inferno Drainer"](https://muellerberndt.medium.com/a-peek-inside-inferno-drainer-0a69647b85ca) (page returned HTTP 403 on direct fetch; details taken from search-engine snippets of the article)
- Angel Drainer (April 2024 sample): payload is "a lengthy base64-encoded string" at the end of a JS file containing xz-compressed JavaScript obfuscated with obfuscator.io, decompressed at runtime by a WebAssembly decompressor; it "overrides the request method to redirect the victim's RPC calls. Instead of using the Ethereum provider, it forwards the call to Metamask via window.postMessage", explicitly to defeat extensions (WalletGuard, Pocket Universe) that "operate by proxying the request method of the Ethereum provider object" — [Mueller, "A brief analysis of Angel Drainer"](https://muellerberndt.medium.com/a-brief-analysis-of-angel-drainer-1660d15c9248) (HTTP 403 on fetch; from search snippets)
- Blockaid's generic description of modern drainers: they "monitor for inspection actions such as right-clicking or opening Chrome's developer tools" and then redirect, close the tab or clear the console; use API hooking to block devtools, debugger detection that terminates, and breakpoint traps; control-flow/data/string obfuscation; many sites are controlled by one central server allowing "dynamic updates and remote execution of malicious code"; the server collects wallet address, IP, country, assets and sites visited, and "builds the transaction expected to yield the highest profit", so the client never contains the draining logic — [Blockaid, Malicious dApp 101](https://blockaid.io/post/malicious-dapp-101-wallet-drainers-are-stealthier-more-complex-than-ever)
- Cloaking in a crypto phishing platform (CryptoGrab, Abnormal Security): cloaking layer hides the page from scanners, CAPTCHA challenges and IP blacklisting block security bots, and "generates unique phishing pages through dynamic content and JS obfuscation" — [Abnormal Security](https://www.abnormal.ai/blog/cryptograb-cryptocurrency-fraud-scam-websites-phishing)
- CLINKSINK (Solana): on load checks that Phantom is installed (analysed variant Phantom-only; others multi-wallet); config strings "Sign Up / Sign In with Phantom", "Claim Now", "Desktop required"; C2 flow = POST affiliate ID (encrypted with hardcoded key) → AES-encrypted config (Telegram chat ID + JSON with `receiver`, `min_value_assets`, `min_value_connect`, `split`, `split_address`, `redirect_if_not_installed`, `solana_price`) → POST wallet address for balance lookup (server returns `null` for repeat wallets) → victim prompted to sign. Mandiant's YARA rule `M_Utility_CLINKSINK_1` matches on strings `solanaWeb3.Connection`, `solanaWeb3.SystemProgram.transfer`, `solanaWeb3.Transaction`, `.Token.createTransferInstruction(`, `.Token.createAssociatedTokenAccountInstruction(`, `.isphantom`, `phantom.app`, and function names `async function createTxs(`, `createPrizeTxs(`, `claimSolana(`, `connectSolana(`, `waitForWalletConnection(`, `getTokenBalance(`, `createTokenTxs(`, `updateMintText(`, `updateConnectText(` (condition: 5 of the function names, or 3 crypto strings + any phantom string + 3 transaction strings) — [Google Cloud / Mandiant](https://cloud.google.com/blog/topics/threat-intelligence/solana-cryptocurrency-stolen-clinksink-drainer-campaigns)
- Check Point 2023 Angel case: freshly deployed attacker contracts "with no transaction history, used to evade wallet alerts"; selectors seen: Permit `0xd505accf` (spender = attacker contract, value effectively unlimited), `transferFrom 0x23b872dd`, entry function `0x095838d2` that checks for code at an address and deploys if none exists — [Check Point Research 2023](https://research.checkpoint.com/2023/the-rising-threat-of-phishing-attacks-with-crypto-drainers/)

**Public IOC / signature feeds**

### Inferences
- Static page-side fingerprints that a content script can cheaply test: (1) `<script src>` basename patterns — UUID-named local JS, `settings.js`+`webchunk.js`, `contract.js`+`main.js`+`vendor.js`, `scripts/seaport.js`, `scripts/wallet_connect.js` — combined with CDN loads of `ethers` UMD + `merkletreejs` + `sweetalert2` on a page that is not an established dApp; (2) very large single scripts (multi-MB) with high string entropy and `debugger` density; (3) presence of base64 blobs decoded via WebAssembly at runtime. These are brittle (kits rename files) and should be weighted, not decisive.
- Runtime network-side fingerprints usable from an extension: page-originated JSON-RPC `eth_call` to BSC public RPCs when the page's own chain context is not BSC; `aggregate3` multicalls with `allowFailure:true` to Multicall3; requests to PHP endpoints with `?e=`; POST bodies whose first bytes decode to the OpenSSL `Salted__` header; requests to `*.workers.dev` / `*.koyeb.app` from a page with a "claim/airdrop" lure. A content script can observe some of these only via `PerformanceObserver` resource entries (URLs, not bodies); request bodies require `webRequest` (non-blocking in MV3) in the service worker.
- Because drain logic is server-built, the client script reliably exhibits a "telemetry-then-prompt" pattern: connect → POST wallet address to a non-dApp origin → delayed signature/transaction request whose payload arrives from the network. Timing correlation (network response immediately followed by a `request()` call) is a strong behavioural signal.
- Anti-devtools behaviour (contextmenu blocked, `debugger` loops, console clearing) is rare on legitimate dApps and is itself a signal.

### Gaps
- No public, maintained YARA/regex signature pack exists for EVM drainer JS (CLINKSINK is the only vendor-published YARA rule found). The IMC'25 867-fingerprint dataset is not published in the paper text I could read.
- Could not fetch Mueller's two Medium articles (HTTP 403) or Blockaid's AngelX technical details; the Angel postMessage bypass is known only from search snippets. No primary source describes Ace, Nova or Medusa front-end code; the AMLBot Medusa report is behind a download form.
- No source found describing current (2026) kit file names; the IMC'25 fingerprints reflect 2023–early 2025 toolkits.

## KQ2. Wallet-interaction behaviour and what a MAIN-world `document_start` content script can observe

### Takeaway
Drainers converge on a small set of wallet calls — connect, (optional) `wallet_switchEthereumChain`, then one of: ERC-20 `approve`/`increaseAllowance`, `setApprovalForAll`, Permit/Permit2 via `eth_signTypedData_v4`, Seaport/Blur zero-price listing signatures, a payable `claim`/`mint`/fallback call that is really a native transfer, EIP-7702 delegation + batch, or on Solana a multi-transfer / `SetAuthority` transaction. All of these pass through `provider.request()` (EIP-1193) or `window.solana.signTransaction/signAllTransactions`, so a MAIN-world script running at `document_start` can wrap them — but Angel demonstrated a bypass by talking to MetaMask's content script via `window.postMessage` directly, so provider wrapping must be paired with a `message` listener / EIP-6963 interception, and the extension should assume wrapping can be detected and evaded.

### Cited Findings
- EIP-1193 provider is the standard dApp↔wallet interface; dApps are told to request accounts only on user action: "Only trigger connection requests in response to user actions (like selecting a button). Never auto-connect on page load." and `eth_requestAccounts` "should only be made in response to user interaction... otherwise the user may be spammed" — [MetaMask docs: authenticate users](https://docs.metamask.io/sdk/guides/authenticate-users); [MetaMask docs: access accounts](https://docs.metamask.io/wallet/how-to/access-accounts)
- EIP-6963: dApp adds a listener for `eip6963:announceProvider`, dispatches `eip6963:requestProvider`; wallets announce `{info:{uuid, name, icon, rdns}, provider}`. `rdns` is self-attested so wallets can impersonate each other; duplicate `uuid`s suggest tampering; SVG icons can run JS; wallets may `Object.freeze` providers; wallets may delay injecting `window.ethereum` until requested — [EIP-6963](https://eips.ethereum.org/EIPS/eip-6963)
- Signature types used by 2025 drainers (>$1M cases): Permit/Permit2 3 cases $8.72M (~38%), approve/increaseApproval 3 cases $5.62M, direct transfer 2 cases $4.87M, EIP-7702 batch 2 cases $2.54M, setApprovalForAll 1 case $1.23M; largest single theft $6.5M via a Permit signature; "Permit signatures remained the dominant type" — [ScamSniffer 2025](https://drops.scamsniffer.io/scam-sniffer-2025-crypto-phishing-losses-fall-83-to-84-million/). In 2024, 56.7% of drainer thefts used Permit signatures — [Ryder citing ScamSniffer](https://ryder.id/blogs/post/wallet-drainers-took-494m-in-2024-heres-how)
- Permit2 mechanics: victim signs an off-chain message; the signature grants Permit + TransferFrom inside the Permit2 contract; "nothing shows up on-chain until the attacker submits it"; example $1.39M PEPE/MSTR/APU theft moved within an hour — [Decrypt](https://decrypt.co/286076/pepe-uniswap-permit2-phishing-attack). Permit is built on EIP-712 typed data — [spark.money](https://www.spark.money/glossary/permit-signature)
- Inferno (2025) requested: ERC-20 `approve` to a fake token contract (often unlimited) followed by `transferFrom`; Permit2/permit signatures "when the victim lacks native gas"; direct transfer to a fake token contract; native transfer to a CREATE2-precomputed, not-yet-deployed address later deployed by a factory (`0xed0e416e0fEEA5b484ba5c95d375545AC2b60572` on Ethereum); "Verify"/"Claim" calls to undefined selectors `0x143087ee` / `0x3158952e` on fake tokens whose fallback forwards value; >500 fake tokens share bytecode, each used <1 day; log events include `switch_chain_prompt` and `verify_sign_prompt` — [Check Point Research](https://research.checkpoint.com/2025/inferno-drainer-reloaded-deep-dive-into-the-return-of-the-most-sophisticated-crypto-drainer/)
- IMC'25: ETH is stolen by tricking victims into "calling a payable function named 'claim' or 'mint'" (Angel: payable `Claim(address affiliate)`; Inferno: payable fallback; Pink: payable function); ERC-20/NFTs via approve then operator `multicall` + `transferFrom`; profit split executed inside the contract (`claimRewards` transferring 20%/80%) — [IMC'25 paper](https://assets.blocksec.com/pdf/1761189308551-2.pdf)
- NFT path: Venom targets Seaport and Blur listings "priced at or near zero"; signing one lets the attacker take the NFTs — [ScamSniffer](https://drops.scamsniffer.io/new-scam-as-a-service-provider-venom-drainer/); MetaMask: listing on Blur requires approving the marketplace to act on NFTs and attackers exploited bulk listing — [MetaMask support](https://support.metamask.io/privacy-and-security/staying-safe-in-web3/signature-phishing); `setApprovalForAll` grants an operator control over every token in a collection until revoked — [DEXTools](https://www.dextools.io/tutorials/setapprovalforall-nft-approval-drain-explained)
- EIP-7702 (post-Pectra, 7 May 2025): the victim "signed what looked like a token swap, but the signature authorized delegation to an attacker-controlled implementation and included a batch of token approvals and transfers"; >97% of 7702 delegations were linked to identical sweeper contracts ("CrimeEnjoyor"); SlowMist advises wallets to "prominently display the target contract" of a delegation — [Zealynx](https://www.zealynx.io/research/smart-contracts/eip-7702-wallet-security); [The Block / Wintermute](https://www.theblock.co/post/356481/wintermute-warns-pectra-upgrade-leaves-ethereum-users-at-risk-of-automated-attacks)
- Solana phishing transaction patterns (SolPhishHunter, 2025): (1) STMT — a single transaction with multiple `Transfer` instructions draining ≥2 tokens to zero (one example had five transfers); (2) AAT — `Assign` / `SetAuthority` (account owner) to take over wallet/token accounts; (3) ISA — recipients impersonating system accounts (prefix "Compu", suffix "1111"); 14 STMT transactions used `advanceNonce` (durable nonce) to pre-stage transactions; rule precision 93.96% on 8,571 flagged txs; recall not reported. The paper does not analyse page JS or `signAllTransactions` — [arXiv 2505.04094](https://arxiv.org/html/2505.04094v1)
- Solana wallets (Phantom, Solflare, Backpack) simulate every transaction, but "some sophisticated drainers attempt to detect when a transaction is being simulated... and behave differently" — [madeonsol](https://madeonsol.com/blog/solana-wallet-drainer-protection) (vendor blog, unverified)
- Extension bypass: Angel "overrides the request method... forwards the call to Metamask via window.postMessage", hiding activity "from anti-phishing extensions unless the domain is explicitly blocklisted"; the targeted extensions "operate by proxying the request method of the Ethereum provider object" — [Mueller](https://muellerberndt.medium.com/a-brief-analysis-of-angel-drainer-1660d15c9248) (snippets only)
- Inferno computes a counterfactual (not-yet-deployed) destination address client-side and sends it to the backend "to evade anti-phishing browser extensions" — [Mueller, Inferno](https://muellerberndt.medium.com/a-peek-inside-inferno-drainer-0a69647b85ca) (snippet); Check Point: "a transfer target that doesn't exist on-chain can't be on a blocklist yet" — [Check Point Research](https://research.checkpoint.com/2025/inferno-drainer-reloaded-deep-dive-into-the-return-of-the-most-sophisticated-crypto-drainer/)
- Chrome MV3: content scripts default to `world: "ISOLATED"`; `run_at: "document_start"` runs "before any other DOM is constructed or any other script is run"; in MAIN world "the CSP of the page applies"; MAIN-world scripts have no extension APIs and must relay via `window.postMessage` to an isolated-world script (which should check `event.source`) — [Chrome content scripts docs](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts); MDN: in the page world "the web page can detect and interfere with the executed code" — [MDN content_scripts](https://developer.mozilla.org/en-US/Add-ons/WebExtensions/manifest.json/content_scripts); a wallet developer reported needing `chrome.scripting.registerContentScripts({runAt:'document_start', world:'MAIN'})` because the static manifest `world` was unreliable in an older Chrome — [davidwalsh.name](https://davidwalsh.name/inject-global-mv3)
- Wallet-side simulation reference points: Blockaid transaction simulation P99 <300 ms, plus address-threat DB checks (malicious addresses, address poisoning, OFAC) — [Blockaid wallet security](https://blockaid.io/use-cases/wallet-security); Blockaid dApp scanning "fully simulates all user interactions on any dApp" and crawls >15M sites/day — [SecurityWeek](https://www.securityweek.com/blockaid-emerges-from-stealth-with-33-million-investment/) (vendor claims)
- Wallet Guard (acquired by Consensys July 2024; extension sunset 31 March 2025) described its "Stormwatcher" pre-connect drainer detector as ML over "the website's content, structure, and behavior patterns", motivated by the fact that "scammers can simply spin up a new URL with the exact same scam website template" — [Wallet Guard Stormwatcher](https://www.walletguard.app/blog/stormwatcher); its Snap used "the same security engine as the Chrome extension" — [npm wallet-guard-snap](https://npmjs.com/package/wallet-guard-snap)

### Inferences
- Observable from a MAIN-world `document_start` wrapper: every `request({method, params})` on `window.ethereum` and on each EIP-6963-announced provider (intercept `eip6963:announceProvider` events and wrap `detail.provider` before the page's listener runs — possible only if the wrapper's listener is registered first, which `document_start` guarantees for static scripts), `window.solana.connect/signTransaction/signAllTransactions/signMessage`, and legacy `send/sendAsync/enable`. Payload-level signals: `eth_requestAccounts`/`wallet_requestPermissions` within N ms of load with no preceding user gesture (`navigator.userActivation.isActive` false); `wallet_switchEthereumChain`/`wallet_addEthereumChain` immediately after connect; `eth_signTypedData_v4` whose `primaryType` is `Permit`, `PermitSingle`, `PermitBatch`, `PermitTransferFrom`, `OrderComponents`/`BulkOrder` (Seaport), `Order` (Blur) with `consideration`/price ≈ 0 or `spender` not a known router; `eth_sendTransaction` data starting with `0x095ea7b3` (approve) with max uint value, `0x39509351` (increaseAllowance), `0xa22cb465` (setApprovalForAll, true), or a selector not in any known ABI (`0x143087ee`, `0x3158952e`) with non-zero `value`; EIP-7702 `authorizationList` / `wallet_sendCalls` batches that mix approvals and transfers; Solana transactions containing ≥2 SystemProgram/SPL transfers to the same new recipient or a `SetAuthority`.
- The wrapper must also listen to `window.postMessage` traffic to detect pages that bypass `provider.request()` and talk to the wallet's content-script bridge directly (Angel technique); a page that posts wallet-protocol-shaped messages (e.g. MetaMask's `metamask-provider` stream / `target: "metamask-contentscript"`) without going through `request()` is itself a high-confidence signal, because legitimate dApps use the public provider API. (The exact message shape is wallet-specific and not sourced here.)
- Wrapping is detectable: pages can compare `provider.request.toString()` against native-function output or check for property descriptors. Use a `Proxy` with `Function.prototype.toString` patched or avoid redefining — but accept that a motivated kit can detect it; treat detection-evasion attempts (access to the wrapper's internals, `toString` checks on `request`) as signals too.
- Not observable from the page: the wallet's own UI, simulation results, and the final signed payload; pre-deployment (counterfactual) destination addresses defeat address blocklists, so the extension should score *intent* (payable call to a contract with no code / no history, an approve to a fresh spender) rather than only match addresses — which requires an RPC/`eth_getCode` lookup from the service worker.

### Gaps
- No public document was found describing exactly how ScamSniffer's current (2024–2026) extension or Blockaid's browser integrations hook the provider; the open-source `scamsniffer/scamsniffer` repo dates from 2023 and its README was not readable in this pass.
- No source documents drainer use of `wallet_requestPermissions`, EIP-6963 spoofing by drainer pages, or auto-firing `eth_requestAccounts` on load; only MetaMask's best-practice guidance implies the discriminating value.
- No source quantifies how often Solana drainers call `signAllTransactions` versus `signTransaction`.

## KQ3. Page text / DOM heuristics (urgency, "connect to check eligibility", countdowns, cloning, link graph, anti-inspection)

### Takeaway
Practitioner sources consistently cite the same page-side cues — "claim/verify/migrate/sync" verbs next to a connect-wallet button, fake countdowns, cloned templates reused across fresh domains, young domains with valid Let's Encrypt certs, outbound-link isolation, and right-click/devtools blocking — but no published study measures precision/recall for these Web3-specific heuristics; the only numeric result on cloned-page similarity is Jail-Phish (98.61% accuracy, generic phishing, favicon as one of several features).

### Cited Findings
- Drainer lure vocabulary: IMC'25 built its CT-log monitor on 63 keywords "such as 'claim', 'airdrop', or 'mint'" plus Levenshtein ratio >0.8 variants, and affiliates "clone the websites of popular projects" — [IMC'25 paper](https://assets.blocksec.com/pdf/1761189308551-2.pdf)
- Inferno 2025 lures: fake Collab.Land "verify-here" channel bot and landing paths like `/collab?token=...&server=...&user=...&avatar=...`; fake $TRUMP airdrop sites; the fake bot page warns it will access username/avatar/banner, whereas the real Collab.Land explains signing is off-chain and gas-free — [Check Point Research](https://research.checkpoint.com/2025/inferno-drainer-reloaded-deep-dive-into-the-return-of-the-most-sophisticated-crypto-drainer/)
- CLINKSINK page strings: "Sign Up / Sign In with Phantom", "Claim Now", "Desktop required"; lures impersonated Phantom, DappRadar, BONK, $PHNTM — [Mandiant](https://cloud.google.com/blog/topics/threat-intelligence/solana-cryptocurrency-stolen-clinksink-drainer-campaigns)
- Threat-intel scanner verdicts list: "'Connect wallet' paired with a high-urgency action ('claim', 'migrate', 'revalidate', 'verify', 'sync')", "WalletConnect prompt surfaced alongside an airdrop / giveaway claim", "fake countdown timers and repeated wallet-connect buttons" — [malwaretips scanner page](https://tools.malwaretips.com/url-scan/en.allwallet-claims.com) (automated verdict page, not a study)
- Cloned templates: "Scammers can simply spin up a new URL with the exact same scam website template" — [Wallet Guard](https://www.walletguard.app/blog/stormwatcher); phishing sites "act as reverse proxy mirrors... often have valid SSL certificates from services like Let's Encrypt", so TLS status is not a signal — [Tangem/Blockaid](https://tangem.com/en-GB/blog/post/scam-detection-dapps/)
- Anti-inspection on drainer pages: monitor right-click and devtools opening, then redirect / close tab / clear console; API hooking to block devtools — [Blockaid](https://blockaid.io/post/malicious-dapp-101-wallet-drainers-are-stealthier-more-complex-than-ever); Inferno uses dynamically built `debugger` functions — [Check Point Research](https://research.checkpoint.com/2025/inferno-drainer-reloaded-deep-dive-into-the-return-of-the-most-sophisticated-crypto-drainer/); cloaking + CAPTCHA + IP blacklisting against scanners — [Abnormal Security](https://www.abnormal.ai/blog/cryptograb-cryptocurrency-fraud-scam-websites-phishing)
- Generic red flags (Group-IB): newly registered / misspelled domains, links from ads or DMs rather than official channels, requests for broad spending approval "especially for simple actions like claiming an airdrop", requests for seed phrases, unsolicited airdrops/giveaways and urgent security warnings — [Group-IB](https://www.group-ib.com/resources/knowledge-hub/crypto-wallet-drainers/)
- Domain age as a heuristic is weakening: some attackers register domains shortly before use, and a 75-day-old domain was still a drainer — [malwaretips scanner](https://tools.malwaretips.com/url-scan/en.allwallet-claims.com)
- Favicon/clone similarity: Jail-Phish compares a suspect page with the legitimate domain found via search, scoring similarity of favicons, logos, images, scripts and styles: 98.61% accuracy, 97.77% TPR, FPR <0.64% (generic phishing, not Web3) — [Rao & Pais, Jail-Phish](https://idr.nitk.ac.in/items/242f775b-67c1-43c5-a1b2-9d0c82755307/full); Bolster: cloned kits "often leave the original favicon in place", hash comparison is efficient — [Bolster](https://bolster.ai/blog/how-to-use-favicons-to-find-phishing-websites)
- Legacy MetaMask phishing-warning bypass: a page could cancel the redirect with `window.stop()` (Cure53, 2017, MM-01-002) — [Cure53 report](https://cure53.de/pentest-report_metamask.pdf); clickjacking of the warning page fixed in v10.14.6 — [SlowMist](https://slowmist.medium.com/metamask-clickjacking-vulnerability-analysis-f3e7c22ff4d9)
- Deobfuscation state of the art: JSimplifier (NDSS 2026) taxonomy of 20 obfuscation techniques; "commercial OB protection" (obfuscator.io) and LLM-obfuscated code are the hardest; dynamic sandboxed execution is required for runtime-dependent string decoding — [arXiv 2512.14070](https://arxiv.org/html/2512.14070v1)

### Inferences
- A practical DOM feature set for a content script: (a) lexical — count of {claim, airdrop, eligib*, verify, migrate, sync, revalidate, reward, free mint, whitelist} within 300 px / same container as a button whose text matches /connect|claim|verify/; countdown timers (elements updating every second with `mm:ss` text) that reset on reload; (b) structural — page is a single HTML with few internal routes, all `<a href>` targets resolving to the same origin or to `#`, social links absent or pointing to the impersonated brand's real Twitter/Discord while the page origin differs; `<title>`/`og:site_name`/favicon hash matching a known brand from a local brand table while `location.host` is not on that brand's allowlist (favicon hash tables are cheap to ship); (c) anti-inspection — `contextmenu`/`keydown` listeners that `preventDefault` on F12/Ctrl+Shift+I, `debugger` statements observed via function source scanning, `console.clear` in a timer; (d) script inventory — large inline/local obfuscated scripts, WASM instantiation of a decompressor, `ethers`/`web3`/`@solana/web3.js` loaded on a page whose registrable domain has no history.
- Cloaking means scanner-side (headless crawler) features will miss what the user sees; evaluating in the real user's tab (content script) is an advantage because the drainer must reveal itself to the victim.
- All these features should be combined probabilistically; no single heuristic is validated.

### Gaps
- No peer-reviewed study with precision/recall for Web3-specific page heuristics (urgency text, connect-to-check-eligibility, countdowns) was found; vendor ML systems (Stormwatcher, Blockaid) publish no metrics.
- No source quantifies how often drainer pages disable right-click or how many legitimate dApps do.

## KQ4. Visual similarity / logo detection (PhishIntention, VisualPhishNet, Phishpedia) — feasibility in an extension

### Takeaway
Reference-based visual detectors are accurate (PhishIntention: recall 0.9 at FPR 10⁻³ on a 277-brand target list) and fast on a server GPU (0.26–0.69 s per page), but they rely on Faster R-CNN logo detectors and ResNetV2-50 Siamese backbones plus screenshot capture, none of which has published browser/ONNX ports or model-size figures; a new 2026 paper also shows delayed-rendering evasion defeats them. For an MV3 extension, perceptual-hash / favicon-hash approaches and a small client-side text model are the realistic path; heavy CNN inference would need an offscreen document or WebGPU, which Chrome's docs do not address.

### Cited Findings
- PhishIntention (USENIX Security 2022): components = Abstract Webpage Layout (AWL) detector (Faster R-CNN), OCR-aided Siamese logo matcher (ResNetV2-50 appearance branch + text-shape branch, pre-trained on Logo2K+ 167,140 logos / 2,341 brands), CRP (credential-requiring page) classifier (ResNetV2-50), and a CRP-locator; target list of 3,061 logos from 277 brands; "at a low FPR of 10⁻³, PhishIntention achieves a recall of 0.9, which is more than twice the recall of Phishpedia"; mean/median runtime 0.58 s/0.69 s vs Phishpedia 0.39/0.41 s, EMD 1.23/1.20 s, PhishZoo 65.45/21.93 s, VisualPhishNet 0.26/0.23 s — [PhishIntention paper](https://gangw.cs.illinois.edu/class/cs562/papers/PhishIntention-sec22.pdf); repo still maintained (last push Jan 2026) — [gittrend](https://gittrend.io/repo/lindsey98/PhishIntention)
- Phishpedia repo: logo detector `models/rcnn_bet365.pth` + `faster_rcnn.yaml`, Siamese `resnetv2_rgb_new.pth.tar`, target list expanded to 277 brands, ships a `Plugin_for_Chrome/` and a `WEBtool/`; no model sizes or latency given — [Phishpedia GitHub](https://github.com/lindsey98/Phishpedia)
- VisualPhishNet (CCS 2020): triplet CNN similarity over whole-page screenshots — [VisualPhishNet](https://gangw.cs.illinois.edu/class/cs562/papers/VisualPhishNet-ccs20.pdf)
- PhishLang (client-side MobileBERT text model) reports PhishIntention needing a 348 KB per-prediction artifact and 10.7 s prediction time in its comparison, versus 7 KB / 0.9 s for PhishLang — [arXiv 2408.05667](https://arxiv.org/pdf/2408.05667) (the 10.7 s figure conflicts with PhishIntention's own 0.58 s; PhishLang likely measures end-to-end including capture on CPU)
- PhishSnap (2025) argues visual approaches "depend on deep CNNs hosted on remote servers, raising latency and privacy concerns" and proposes perceptual hashing instead — [arXiv 2512.02243](https://arxiv.org/html/2512.02243v1)
- "I can't recognize (yet): Delayed Rendering to Defeat Visual Phishing Detectors" (2026) — visual detectors can be evaded by rendering brand content late — [alphaxiv 2605.00183](https://www.alphaxiv.org/abs/2605.00183)
- MV3 constraints: service worker killed after 30 s idle; a single event/API call >5 min is terminated; fetch responses >30 s terminate it; global state (loaded models) lost on shutdown; keep-alive via ports (Chrome 114+), WebSockets (116+), offscreen-document messages (109+) — [Chrome SW lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle). Offscreen documents: hidden DOM page, reasons include `DOM_SCRAPING`, `WORKERS`, `BLOBS`, `IFRAME_SCRIPTING`; one per extension; no lifetime limit except `AUDIO_PLAYBACK`; only the `runtime` API; must be a bundled static HTML — [Chrome offscreen API](https://developer.chrome.com/docs/extensions/reference/api/offscreen). Remotely hosted code is disallowed in MV3 ("we will disallow remotely hosted code") — [Chromium blog](https://blog.chromium.org/2020/12/manifest-v3-now-available-on-m88-beta.html)

### Inferences
- A ResNetV2-50 backbone is roughly 100 MB in FP32 (common knowledge, not sourced here) and a Faster R-CNN detector is larger; shipping both in an extension package and running them per page load on CPU/WebGPU would be slow and memory-heavy, and screenshot capture (`chrome.tabs.captureVisibleTab`) requires `activeTab`/`<all_urls>` and only sees the viewport. The practical extension design is: favicon + `og:image`/logo `<img>` perceptual hashes compared against a small table of frequently impersonated Web3 brands (MetaMask, Phantom, Uniswap, OpenSea, Blur, Collab.Land, LayerZero/zkSync/Arbitrum airdrops), plus text-model scoring; defer CNN matching to an optional offscreen document with WebGPU/ONNX Runtime Web if accuracy demands it.
- Delayed-rendering evasion means visual checks should re-run on DOM mutation / before the first wallet `request()` rather than once at load.

### Gaps
- No published numbers for Phishpedia/PhishIntention model file sizes, parameter counts, or any ONNX/WebGPU browser port; the Phishpedia `Plugin_for_Chrome` internals were not examined.
- No source on WebGPU/WASM inference inside MV3 offscreen documents specifically.

## KQ5. What legitimate mint / airdrop / quest / claim flows look like, and which signals they do NOT exhibit

### Takeaway
Legitimate flows share surface features with drainers (connect button, "claim"/"mint" verbs, countdowns, signature prompts) but differ in payload: a real mint sends value to a known, long-lived, verified minting contract and calls a public ABI (`mint`), a real eligibility checker reads an address without any signature, a quest/login uses a plain EIP-4361 (SIWE) `personal_sign` whose `domain` equals the page origin, and legitimate NFT listing/permit signatures name a well-known verifying contract with non-zero prices. Drainers instead produce approvals/permits to fresh spenders, zero-price orders, payable calls to unknown selectors, chain switches before any user intent, and telemetry to non-dApp origins.

### Cited Findings
- Manifold claim pages mint under the creator's own Manifold Creator contract, via a Lazy Claim extension contract; for ETH-priced claims the user calls `mint` sending the full price as `value`; for USDC-priced claims the user first approves USDC spending then calls `mint` with only the Manifold fee as value — [Manifold docs: Claim Page](https://docs.manifold.xyz/manifold-studio/apps/claim-page); [Farcaster mini-app tutorial](https://paragraph.xyz/@keccers/how-to-mint-manifold-1155s-in-a-farcaster-mini-app); [Zenn article on Lazy Claim contracts](https://zenn.dev/nekoze_da/articles/how-to-claim-manifold-nft-using-ethers)
- Magic Eden: Solana dApps "most commonly" use the Solana Wallet Adapter; Launchpad accepts only ~3% of applications and provides custom minting contracts and whitelist management — [Magic Eden docs](https://docs.magiceden.io/docs/diving-into-solana); [nftnow](https://nftnow.com/guides/a-guide-to-magic-eden-solana-nft-marketplace/) (secondary)
- Sign-In with Ethereum (EIP-4361): message begins "<domain> wants you to sign in with your Ethereum account:" followed by address, optional statement, URI, Version 1, Chain ID, Nonce (≥8 alphanumeric), Issued At, optional Expiration; signed via ERC-191 (`\x19Ethereum Signed Message:\n`); "Wallets must verify the request origin against the `scheme` and `domain` fields to prevent phishing"; for an iframe the iframe's origin applies — [EIP-4361](https://eips.ethereum.org/EIPS/eip-4361); CDP docs: nonce + expiry + domain binding guard against cross-site replay — [Coinbase CDP SIWE](https://docs.cdp.coinbase.com/wallets/authentication/siwe)
- MetaMask guidance for dApps: connect only on user action, never auto-connect on load; disable the connect button while a request is pending — [MetaMask docs](https://docs.metamask.io/sdk/guides/authenticate-users); [MetaMask docs](https://docs.metamask.io/wallet/how-to/access-accounts)
- Legitimate `setApprovalForAll`: "a first marketplace listing as the only typical legitimate case" — [browser.lol commentary](https://browser.lol/en/blog/web3-wallet-drainers-how-one-signature-empties-your-crypto) (opinion); Blur listings require approving the marketplace — [MetaMask support](https://support.metamask.io/privacy-and-security/staying-safe-in-web3/signature-phishing)
- Galxe (Oct 2025) front-end/DNS hijack: Galxe told users not to connect wallets; funds were safe "as long as they didn't approve any transaction"; projects advised revoking permissions previously given to Galxe contracts — [Blockworks](https://blockworks.co/news/glaxe-dns-attac); [coinpost](https://coinpost.jp/?p=485210). This shows that a trusted quest platform normally does ask for connections and sometimes approvals, so origin trust alone is insufficient.
- Legitimate transaction simulation is standard on Solana wallets (Phantom, Solflare, Backpack simulate every transaction) — [madeonsol](https://madeonsol.com/blog/solana-wallet-drainer-protection)
- Real Collab.Land verification: "signing is off-chain and costs no gas" (vs fake bot which warns about accessing Discord profile and redirects) — [Check Point Research](https://research.checkpoint.com/2025/inferno-drainer-reloaded-deep-dive-into-the-return-of-the-most-sophisticated-crypto-drainer/)
- IMC'25 attack contracts: victim calls payable `Claim`/`mint`/fallback on a profit-sharing contract that immediately forwards 20/80 — i.e. the "mint" never returns a token — [IMC'25 paper](https://assets.blocksec.com/pdf/1761189308551-2.pdf)

### Inferences — discriminating table (drainer-only vs shared vs legit-only)
- Shared (do NOT use alone): connect-wallet button; words "claim", "mint", "airdrop", "eligible"; countdowns (real mints have phases); `personal_sign` prompt (SIWE login on Galxe/Layer3/Zora-style apps); `eth_sendTransaction` with `value` (real mints are payable); `wallet_switchEthereumChain` (real multi-chain dApps switch after the user picks a chain); `setApprovalForAll` (first listing on OpenSea/Blur/Magic Eden); EIP-712 `Permit`/`PermitSingle` (Uniswap, 1inch and Permit2-based swaps use them).
- Drainer-leaning payload signals: approve/permit where `spender` is a contract with `eth_getCode == 0x` or deployed < 1 day ago, or an EOA; `value` == max uint on a page not presenting a swap; Seaport/Blur orders with zero consideration; payable call whose selector is not in the 4-byte directory and whose target has no verified source; `mint` call whose target has no ERC-721/1155 interface (no `supportsInterface`), or whose `to` is a contract that forwards all value (profit-sharing pattern); native transfer to an address with no code and no history as the *first* action after connect; signature request within seconds of connect with no intervening user click; chain switch *before* any user click; EIP-7702 delegation to an address that is not a known smart-account implementation; Solana transaction with ≥2 transfers emptying balances or `SetAuthority`/`Assign`, or `signAllTransactions` with many transactions on a claim page.
- Drainer-leaning context signals: page POSTs the connected address to an origin that is neither the page origin nor a known RPC/indexer immediately after connect (Inferno `walletAddress` telemetry; CLINKSINK balance lookup); the page requests balances of many tokens via `eth_call`/`alchemy_getTokenBalances` right after connect *and* then shows a signature prompt (asset inventory before choosing the drain method); Discord OAuth `/oauth/callback` → landing page with JWT on a non-collab.land domain.
- Legit-only signals (negative weight): SIWE message whose `domain` equals `location.host`; mint target contract verified and older than N days with many prior `mint` calls (needs an RPC/explorer lookup in the service worker); page has working internal navigation, real social links resolving to accounts that link back to the origin; wallet connect triggered by `click` with `navigator.userActivation.isActive === true`; official-domain allowlists (MetaMask `eth-phishing-detect` allowlist, ScamSniffer whitelist).
- Eligibility checkers that only read an address never need `request()` at all beyond `eth_accounts`/`eth_requestAccounts`; any signature request on a page that advertises itself as a "checker" is suspicious.

### Gaps
- No primary documentation found for Zora, Highlight, Layer3 or Galxe front-end call sequences (which exact signatures they request); the SIWE inference is from the standard, not from those apps' code.
- No measurement of false-positive rates of these discriminators on real dApp traffic was found.

## KQ6. How ScamSniffer / Wallet Guard / Blockaid implement on-page detection; MV3 limitations

### Takeaway
Public detail is thin: Wallet Guard and Pocket Universe proxied `window.ethereum.request` to simulate transactions (confirmed indirectly by Angel's bypass), ScamSniffer's current extension is closed-source and combines domain blocklists ("Web3 Safe Browsing"), signature checks and simulation, and Blockaid runs server-side dApp sandboxing + address threat intel that wallets (MetaMask, Safe, Ronin, Zerion, Rainbow) consume. MV3 forces any extension to bundle all detection code, keep models/state in storage or an offscreen document, use non-blocking `webRequest` or `declarativeNetRequest` for network, and rely on MAIN-world `document_start` scripts for provider wrapping.

### Cited Findings
- Wallet Guard: described as an open-source extension "to identify potential scams and wallet drainers before they interact with users' wallets", with simulation as a transaction preview; acquired by Consensys July 2024; sunset 31 Mar 2025; components = extension, MetaMask Snap, dashboard — [Optimism RetroPGF application](https://vote.optimism.io/retropgf/3/application/0xb7247ddd26258c85d25c75b287219c22c72db583a99d9539a962b9b5cccb5194); [Wallet Guard blog](https://www.walletguard.app/blog/stormwatcher); [npm wallet-guard-snap](https://npmjs.com/package/wallet-guard-snap)
- Angel analysis: WalletGuard and Pocket Universe "operate by proxying the request method of the Ethereum provider object to simulate and evaluate" transactions; Angel bypasses them by forwarding via `window.postMessage` — [Mueller](https://muellerberndt.medium.com/a-brief-analysis-of-angel-drainer-1660d15c9248) (snippets)
- ScamSniffer extension listings: "Web3 Safe Browsing with real-time malicious website detection and a Blocklist database", "Real-time signature security checks", "Clear transaction simulation"; freemium (0.25% fee on selected DEX trades for premium) — [extensionauditor](https://extensionauditor.com/scan/scam-sniffer-mnkbccinkbalkmmnmbcicdobcmgggmfc); [chromeboard](https://chromeboard.com/extension/scam-sniffer-mnkbccinkbalkmmnmbcicdobcmgggmfc); old open-source extension AGPL-3.0 (2023) — [GitHub](https://github.com/scamsniffer/scamsniffer); ScamSniffer offers a Permit2 authorization management tool — [Cointelegraph](https://cointelegraph.com/news/victim-eth-restaking-exploit-receives-funds-back-scammers)

### Inferences
- Architecture that fits MV3 and the evidence above: (1) static `content_scripts` entry with `world: "MAIN"`, `run_at: "document_start"`, `match_about_blank`/`all_frames: true` (drainers may run in iframes; SIWE says iframe origin governs) that wraps `window.ethereum`, defines a setter trap for late-injected providers, listens for `eip6963:announceProvider`, wraps `window.solana`/`window.phantom.solana`, and hooks `window.postMessage`/`message` events for wallet-bridge traffic; (2) isolated-world script that collects DOM/text/script-inventory features and relays via `postMessage` with `event.source === window` checks; (3) service worker that holds blocklists/allowlists (`chrome.storage`), does RPC lookups (`eth_getCode`, contract age) with short timeouts, scores, and triggers a warning overlay; (4) optional offscreen document for heavier work. Blocklist feeds (ScamSniffer scam-database GPL-3.0; MetaMask eth-phishing-detect) are data, so fetching them at runtime is allowed under the remote-code rule; model weights are data too.
- Because the SW can be killed mid-analysis, page-level scoring should complete in the content script within a few hundred ms, with asynchronous enrichment (RPC lookups) upgrading the verdict.
